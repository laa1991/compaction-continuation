# 压缩 = 续接，不是还原（设计记录）

> 我们在一个真实、持续在用的 agent 部署里，先量了「压缩到底丢了什么」，然后改了做法：**事实离开摘要、原文保持可指到、摘要用来装还没了结的张力。**

长程 agent 靠**压缩**活着：模型把较早的对话总结成一条摘要，摘要顶替被遮蔽的那一段，工作继续。关于这一步的讨论几乎都在谈**保真**——摘要留得够不够？我们量下来，更有用的问题是**接续**：折叠之后，下一轮还能不能看出**什么还没了结**、什么试过被否掉了、以及精确的值放在哪。

这份仓里是那件事的**设计面**。它不是插件、也不是补丁：它是一份设计记录——把「摘要 = 有损的副本」换成「**摘要 = 导航 + 张力，外加一条指回无损原文的路**」。

## 四条命题

1. **同一个调用里，摘要不可能既压缩又逐字保管。** 我们自己的指令里同时写着「保留精确路径、命令、错误串、数值」，又写着「写简洁的条目，不要散文」「合并旧摘要、丢掉过时的」——**这是两股方向相反的力**，模型每次都倒向压缩。实测一次真实会话：**360 个本地文件路径 + 14 个真错误码**在原文里有、在摘要里没了。
2. **按「压不压得坏」分界，不按话题分界。** 压不坏的（判断、理由、信号、张力）进摘要；一压就坏的（路径、错误码、命令、数值、引文）进一个**不被总结**的地方，摘要只留**指针**。
3. **摘要最值钱的是「张力」，不是「信息」。** 已闭合的事可以反推；没闭合的——待办、卡点、开放问题、承诺——一断就接不上。
4. **事件溯源的 harness 里，原文本来就在盘上。** 问题不是「原文丢了」，是「原文不在模型能看见的地方」。要给的是一条**读得到的路**，不是另建一个仓库。

## 仓里有什么

| 文件 | 是什么 |
|---|---|
| `DESIGN.md` | 设计正文：病灶、分界、段落结构（导航层 + 张力层）、与原文指针的边界、验收判据 |
| `COMPONENTS.md` | 由它长出来的组件清单——每件干什么、服务哪一半；**已落地 / 仍是设计**分开标 |
| `EVIDENCE.md` | 它依据的读数（仪器名、分母、单位），以及长篇报告在哪 |
| `DATA-POLICY.md` | 发布红线：什么可发、什么绝不发 |

## 我们不主张什么

- **只有一个部署。** 这里的每个率都是「一台持续在用的单机 agent 部署」的率；我们主张可迁移的是**设计与仪器**，不是那些率。
- **不是全部已落地。** 段落重排与原文指针已实现且在跑；更后一步的「分层」（把慢变内容整个移出摘要）有读数支撑、**仍是设计**（`COMPONENTS.md` 里区分）。
- **相邻的测量是另一份。** 「压缩丢了多少」的定量读数在 `EVIDENCE.md` 链接的那份报告里，它有它自己的局限声明。
